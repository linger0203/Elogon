两条路径本轮更新：注销仍是同一套解绑动作，但有两条进入路径 ——
  A · 已登录态（菜单栏面板一级入口）：二次确认 → 输入当前账号密码验证身份 → 解绑完成。验证是为了防他人趁电脑未锁屏误注销。
  B · 认证失败态（退出后登录页底部入口，v1.0.7 新增）：二次确认 → 直接解绑，不再验密码。 因为来者已在登录页用真实凭据通过 IAM 认证 —— 他就是「合法员工，但不是本机绑定的那位」， 正是原绑定用户离职、电脑转交他人的场景。原用户的密码此时根本拿不到，照搬 A 的验证方式等于没解这条死锁。
为什么不用 macOS 系统密码验证已否决：macOS 上客户端拿不到也验证不了系统密码 —— LocalAuthentication 只返回布尔结果、且弹的是系统自己的认证面板； Authorization Services 是申请特权操作，同样不向 App 暴露密码。 在自家弹窗里放「请输入系统密码」再本地校验，技术上落不了地。所以验证对象改为由 IAM 回答「你是谁」。
名称：「注销账号」→「注销绑定账号」。加"绑定"二字明确它解除的是绑定关系， 不是注销统一身份账号本身。
为什么需要这条流程：本机 OS 账号与统一身份账号是 1:1 绑定。 系统要凭登录的 OS 账号唯一定位该自动登录哪个 IAM 账号，所以必须严格保持一对一。 这也意味着不能提供「直接换绑」 —— 想换账号只能先注销再绑新的。
绑定记录 · 写入与清空各只有一处本轮新增： 「本机已绑定账号」是绑定记录的读取值，不是写死的常量 —— 写入只发生在「绑定引导窗口」提交成功那一刻，「清空」只发生在本页注销成功那一刻。 「退出登录」不动绑定记录 —— 这正是「退出」与「注销」的分界线。
  它与本机 macOS 账户名是两个字段：前者是绑定关系的右端（用户输进来的 IAM 账号）， 后者是系统给的只读值。设备转交后两者会分离（新员工用自己的 macOS 账户，而绑定记录还留着原员工的 IAM 账号）， 所以注销后返回的「首次绑定」窗口展示的仍是当前 macOS 账户名。
不通知本人维持原裁定：A、B 两条路径都不向原绑定账号推送通知，靠操作日志与服务端记录事后追查。
不需要管理员审批已确认：二次确认 + 身份验证通过即可完成，不挂审批流。
网络异常处理：服务端解除失败时提示重试，本地绑定关系不先行清除， 避免出现「本地以为解绑了、服务端还绑着」的不一致。
